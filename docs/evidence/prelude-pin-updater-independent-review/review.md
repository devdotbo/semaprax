# Source-only review of `update-prelude-forecast-pins.py`

Nothing was run. Line numbers for the updater are quoted statements, since the paste carries no numbering. Other line numbers are my counts from the supplied scopes and may be off by a few lines.

## Blockers

**B1. The graph-digest validation uses the wrong formula and will reject every genuine capture.** The updater's check is `sha(wires[name].replace(field, b"", 1)) == digest`, where `sha` is plain `SHA256(bytes)`.
- The producer, `artifact_digest` (`workspace_graph.rs:3793-3801`), hashes `ARTIFACT_DIGEST_DOMAIN || (len as u64).to_le_bytes() || payload`.
- The domain is `b"semaprax.workspace-semantic-graph.artifact-digest.v1\0"`, including the trailing NUL (`:100`).
- The framing logic is otherwise right. The producer pushes `,"graph_digest":"<d>"` (`:3573-3575`), and the payload hashed at `:~3388` is the same document without that field. `type_proof_tests.rs:~944-946` confirms `artifact_digest(replacen(field)) == graph_digest()`.
- The fix is `sha256(DOMAIN + len(payload).to_bytes(8,"little") + payload)`, with the domain constant copied from `:100`.
- `PROJECT_GRAPH_DIGEST_DOMAIN` (`:102`) is irrelevant here, because `rendered_entry()` goes through the workspace renderer.
- As written the updater fails closed, so it is safe but unusable. Do not "fix" it by dropping the check, since this is the only content binding on the wires. After the fix, add a negative self-test with one flipped byte.

**B2. A 101 exit can mask real failures, not just the stale pin assertions.** The updater accepts exit codes 0 or 101 and checks only that the log contains the selector and `running 1 test`. In the public-graph test, `capture_pin_candidate` runs at `semantic_graph.rs:~577`, before these assertions:
- the revision and schema assertions;
- `assert_public_getters_match_wire` (`~584`);
- the edge-kind set (`~585-599`);
- the later CLI checks, and the read-only/locking/inventory checks that follow the stale assertions (`~602+`).

A getter/wire mismatch, an edge-set regression, or a locking failure would therefore still yield a "complete" capture. If the panic is on an earlier assertion (for example the edge-kind set) rather than the stale `334_016` assertion, the run still counts as an allowed failure.
- Fix: for exit 101, require exactly one `panicked at` in the log. The panic must be the expected stale assertion, matched by its `right:` value (`334016` or the old `sha256:c5cb…`) in the public-graph log. For analysis, match the old-SHA array assertion.
- This is a concrete updater gap, not something ROOT's protocol can cover, because the logs are the only evidence.

**B3. The updater does not authenticate the capture, and `--repo` is unrelated to it.**
- `binaries.json` is only checked for `len >= 2`. There is no expected hash, no role (lib versus workspace), and no per-label binary recorded in `status.tsv`.
- `source-head.txt`, `candidates.json`, and the logs are all generated by the same capture script. The updater compares them only with each other.
- `--expected-capture-head` accepts any prefix of 7 or more characters.
- `--repo` is never tied to the capture head: no `git rev-parse` comparison and no clean-tree check. The capture script also runs `git rev-parse` and `git diff` in whatever cwd it is invoked from.
- Consequence: wires captured from commit X can be applied to a different checkout whose stale literals still match uniquely.
- Minimum fix: require a full 40-hex head, require `--expected-lib-sha256` and `--expected-workspace-sha256` supplied by ROOT and match them against `binaries.json`, and record the binary hash per status row.
- Cannot be proved from this source: that a binary was built from that head. That belongs to ROOT's frozen-build protocol. The report's status string honestly says "requires-wire-review", so keep it that way and do not label it authenticated.

**B4. The source-drift check misses untracked files.** `git diff --binary HEAD` (`capture:~28`) ignores untracked and ignored files, so `source-local.patch` can be empty while the tree differs. This matters for `include_str!` and fixtures, and for files in `src/` or `tests/`. Add `git status --porcelain --untracked-files=all` and require it empty, or record it in the capture. The patch is also taken after the binaries were built, so it proves tree state only at capture time.

## Apply-behavior defects

**A1. The apply is non-atomic.** The drift check sits inside the write loop (`require(read == before…); write_text`). Drift in the second file is detected only after the first file has been rewritten. Verify all files first, then write, ideally via temp files plus rename. Everything else before `mkdir` is validated up front, which is good.

**A2. Text I/O can rewrite files and falsify the report.** `read_text` and `write_text` use the locale encoding and newline translation. A CRLF source would be silently normalized. `source_sha256` is computed from the re-encoded text, not the file's bytes. Use `read_bytes`/`write_bytes`, and hash the raw bytes. Also add after-hashes to the report.

**A3. Minor evidence-directory issues.**
- `evidence` is not checked to be outside `repo` or `capture`. `copytree` into a subdirectory of the capture would recurse.
- The `exists()` then `mkdir` sequence is a small TOCTOU.
- Unexpected extra files under `wires/` are neither rejected nor reported, but are copied.

## Verified as correct

- Exactly 11 edits, derived by construction: 1 builder usage, 1 public-graph SHA, 8 analysis SHAs, 1 projection SHA.
- The eight old analysis literals and order match `semantic_graph.rs:~1040-1047`. The old public-graph literal matches `:~605`.
- All new values are computed from captured bytes with no guessed hashes. `format(amount, "_")` yields `334_016`-style Rust literals. Each `before` must occur exactly once. Nothing is weakened.
- The `0 < amount <= 67108864` check matches `MAX_BUILDER_BYTES` (`:94`).
- `type(amount) is int` rejects bools. The terminal-LF check agrees with `capture`'s line extraction.

## Uncertainties (not shown in the supplied source)

1. The old projection literal `sha256:ba3d1b86…` is outside the pasted scope. It is covered only by the runtime uniqueness check.
2. The `workspace_graph_digest` field name and the `budget.used_builder_bytes` JSON path are unseen. A mismatch fails closed with a `KeyError`.
3. The analysis wires have no independent digest check, only equality with the graph digest.
4. Other stale literals may remain. The projection test may assert builder bytes or a digest literal beyond the replaced SHA, since the comment at `type_proof_tests.rs:~821-823` mentions 421597→419077. The same applies to other numeric assertions in the analysis test before `:~999`. Because assertions are retained, these would fail after apply rather than slip through. A pre-apply grep for old numeric and digest literals would reveal them.
5. If the analysis test panics before the capture loop (`:~1008-1018`), the wires are simply missing and the updater refuses. That is acceptable.
6. The comments at `semantic_graph.rs:~600-601` and `:~1020`, and `type_proof_tests.rs:~821-823`, claim restoration of the original KATs. They become false after apply. The updater does not touch them.
7. If a wasm binary is supplied and the calculator wires are missing, the updater refuses (`missing` is nonempty), and calculator status is not checked. That is consistent but conservative.

## Ownership split

- **Updater owns:** B1, B2, B4, A1, A2, the `--repo`/head binding in B3, and the 40-hex head requirement.
- **ROOT's frozen-build protocol owns:** proving binary-to-source provenance, and the external binary hashes in B3. The updater can only compare against hashes ROOT supplies.
